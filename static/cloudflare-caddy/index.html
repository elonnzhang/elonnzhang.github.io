01 / 分工

不是重复代理，
而是内外分工。

Cloudflare 管理互联网边缘，Caddy 管理主机内部。边界清楚之后，TLS、安全策略、静态文件和多个本地端口都各归其位。

Public edge

Cloudflare
负责“外面”

它是访客首先抵达的公网入口。域名解析和用户侧 HTTPS 在边缘完成，再把经过检查的请求送入 Tunnel。

  • 托管 DNS 与公网主机名
  • 终止用户侧 HTTPS，并提供可选 WAF/CDN
  • 把请求路由到指定的 Named Tunnel
  • 隐藏源站公网 IP，减少绕过边缘的入口
Local router

Caddy
负责“里面”

它只在本机接收 cloudflared 交付的请求，然后根据域名与路径决定返回静态文件，还是转给其他应用。

  • 服务 HTML、CSS、图片等静态资源
  • 按 Host 或 URL 路径反向代理
  • 统一压缩、日志与响应头
  • 让多个服务共用一个本机入口
02 / 行程

一次访问，
经过五站。

从浏览器输入域名到页面出现，请求始终沿着一条明确的单向入口前进。每一站只做自己擅长的事。

  1. 浏览器连接 Cloudflare

    DNS 将 domain 指向 Cloudflare。访客与边缘节点建立 HTTPS 连接，而不是直接连接你的 Mac。

  2. 边缘完成公网处理

    Cloudflare 处理 TLS，并根据已开启的规则执行缓存、安全检查或访问控制，再识别这个域名关联的 Tunnel。

  3. 请求沿 Tunnel 回到本机

    cloudflared 预先从本机向 Cloudflare 主动建立出站连接，因此源站无需为网站开放公网入站 80 或 443。

  4. Caddy 在 {port} 接手

    cloudflared 把请求交给 127.0.0.1:{port}。Caddy 检查 Host 与路径，选择对应的 file_server 或 reverse_proxy。

  5. 内容沿原路返回

    静态页面或应用响应回到 Caddy，再经过 Tunnel 和 Cloudflare 返回浏览器。对访客而言，这仍然只是一次普通的 HTTPS 访问。

03 / 当前实例

一个入口，
分发多个服务。

Cloudflare 只需要记住 Caddy 的入口。真正的静态目录和应用端口都留在主机内部，由 Caddyfile 集中管理。

:{port} LOOPBACK
Incoming request Local target
domain/*主站与静态资源 www/index.html
domain/api/*保留 /api 前缀 127.0.0.1:8080
domain/admin/*移除 /admin 前缀 127.0.0.1:9000
app.domain/*独立应用子域名 127.0.0.1:3000

为什么本机这一跳可以使用 HTTP？ cloudflared 与 Caddy 位于同一台机器，最后一跳只经过 loopback；用户到 Cloudflare 以及 Cloudflare Tunnel 本身仍然是加密连接。如果两者跨主机部署，则应改用经过证书校验的 HTTPS。

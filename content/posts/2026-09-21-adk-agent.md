ADK-Go 源码阅读笔记 · Agent

> 上一篇建立了三层心智模型和 `iter.Seq2` 事件流这条主线。这一篇进入执行核心：Agent 模块。我们从那个只有六个方法的接口出发，看 base agent 如何驱动一次运行，再看 LlmAgent 如何把「模型调用 + 工具调用」拧成一个回合循环，最后过一遍四种工作流 Agent。

## 一、一切的起点：`agent.Agent` 接口

整个框架都挂在这个精简的接口上（`agent/agent.go:44-53`）：

```go
type Agent interface {
    Name() string
    Description() string
    Run(InvocationContext) iter.Seq2[*session.Event, error]
    SubAgents() []Agent
    FindAgent(name string) Agent
    FindSubAgent(name string) Agent

    internal() *agent   // 未导出：外部包无法直接实现本接口
}
```

六个可导出方法，语义都很直白：

- `Name()` / `Description()`（`agent.go:151`、`155`）——身份与描述。
- `Run(InvocationContext)`（`agent.go:163`）——**核心**，返回事件流。
- `SubAgents()`（`agent.go:159`）——子 Agent 列表。
- `FindAgent(name)`（`agent.go:218`）——名字匹配自身则返回自己，否则委托 `FindSubAgent`。
- `FindSubAgent(name)`（`agent.go:225`）——对子 Agent 做 DFS，每个孩子再调它自己的 `FindAgent`。

真正值得停下来的是第七个、未导出的方法 `internal() *agent`（`agent.go:52`，实现 `agent.go:214`）：

> **它让 `Agent` 接口在当前版本无法被模块外的代码直接实现。**

注释（`agent/agent.go:42`）说得很清楚：「未来版本会允许直接实现这个接口。目前 `agent.New` 是正确方案。」这是一个刻意的演进闸门——先用工厂函数收口，等 API 稳定了再放开。于是所有 Agent 都得走 `New`。

## 二、base agent 的驱动循环

`agent.New(cfg Config)`（`agent/agent.go:56-75`）做两件事：校验没有重复的子 Agent，然后构造未导出的 `*agent` 结构体。公开的配置面是 `Config`（`agent.go:78-108`）：

```go
type Config struct {
    Name        string
    Description string
    SubAgents   []Agent
    BeforeAgentCallbacks []BeforeAgentCallback
    Run         func(InvocationContext) iter.Seq2[*session.Event, error]
    AfterAgentCallbacks  []AfterAgentCallback
}

type agent struct {
    agentinternal.State
    name, description    string
    subAgents            []Agent
    beforeAgentCallbacks []BeforeAgentCallback
    run                  func(InvocationContext) iter.Seq2[*session.Event, error]
    afterAgentCallbacks  []AfterAgentCallback
}
```

注意 `Run` 是一个字段——你把「这个 Agent 到底干什么」作为一个函数塞进来，base agent 负责在它前后包裹回调与短路逻辑。这就是 LlmAgent、WorkflowAgent 复用 base agent 的方式（后面会看到）。

`(*agent).Run`（`agent.go:163-212`）是所有 Agent 共享的骨架：
```go
func (a *agent) Run(ctx InvocationContext) iter.Seq2[*session.Event, error] {
    return func(yield func(*session.Event, error) bool) {
        spanCtx, span := telemetry.StartNodeSpan(ctx, ctx, telemetry.OperationAgent{Agent: a})
        yield, endSpan := telemetry.WrapYield(span, yield, func(span trace.Span, event *session.Event, err error) {
            telemetry.TraceAgentResult(span, telemetry.TraceAgentResultParams{
                ResponseEvent: event,
                Error:         err,
            })
        })
        defer endSpan()

        var aa Agent = a
        var newCtx context.Context = ctx.WithContext(spanCtx)

        icDelta := &InvocationContextDelta{Agent: &aa, Context: &newCtx}

        nodeCtx := PromoteWithDelta(ctx, &CommonContextDelta{
            InvocationContextDelta: icDelta,
        })

        event, err := runBeforeAgentCallbacks(nodeCtx)
        if event != nil || err != nil {
            if !yield(event, err) {
                return
            }
        }

        if nodeCtx.Ended() {
            return
        }

        for event, err := range a.run(nodeCtx) {
            if event != nil && event.Author == "" {
                event.Author = getAuthorForEvent(nodeCtx, event)
            }
            if !yield(event, err) {
                return
            }
        }

        if nodeCtx.Ended() {
            return
        }

        event, err = runAfterAgentCallbacks(nodeCtx)
        if event != nil || err != nil {
            yield(event, err)
        }
    }
}
```

流程
```
Run(ctx):
  1. 开 telemetry span，包装 yield 以便追踪每个事件        agent.go:165
  2. 重绑 context，使 ctx.Agent() 指向自己                agent.go:174
  3. event := runBeforeAgentCallbacks(ctx)             agent.go:183
       有 event/err → yield
  4. if ctx.Ended() { return }   ← 短路①               agent.go:190
  5. for event := range a.run(ctx) {                   agent.go:194
        补全 event.Author，yield
     }
  6. if ctx.Ended() { return }   ← 短路②               agent.go:203
  7. event := runAfterAgentCallbacks(ctx)              agent.go:207
       有 event/err → yield
```

两个 `Ended()` 短路点是关键机制。`EndInvocation()` / `Ended()` 在基础上就是一个 bool 的写与读（`agent.go:452-458`）。当某个 before 回调产出了内容，它会调用 `ctx.EndInvocation()`，于是短路① 命中，真正的 `a.run()` 和 after 回调都被跳过。

看 `runBeforeAgentCallbacks`（`agent.go:257-312`）里回调是怎么跑的：

1. **先跑 Plugin 的 before-agent 回调**（`agent.go:264-280`）——全局钩子优先于单 Agent 回调。
2. 再按顺序跑用户传入的每个 `BeforeAgentCallback`（`agent.go:282-300`）。
3. **第一个返回非 nil 内容的回调胜出**：构造事件、填 author/branch/actions、调用 `ctx.EndInvocation()`（`agent.go:277`、`298`）后返回。
4. 若没有内容但改了 state，仍会发一个只带 delta 的事件（`agent.go:303-309`）。

`runAfterAgentCallbacks`（`agent.go:316-374`）结构相同，但有一个刻意的非对称（注释在 `agent.go:356`）：它**不**调用 `EndInvocation()`，因为 after 回调本来就是最后一步，`Ended` 标志也不需要往父级传播。

回调类型签名都很朴素（`agent.go:130`、`138`）：

```go
type BeforeAgentCallback func(Context) (*genai.Content, error)
type AfterAgentCallback  func(Context) (*genai.Content, error)
```

一个 before 回调「结束 invocation」的样子（`agent.go:291-299`，精简）：

```go
event := session.NewEvent(ctx, ctx.InvocationID())
event.LLMResponse = model.LLMResponse{Content: content}
event.Author = agent.Name()
event.Actions = eventActionsFrom(actions)   // 会剥掉 Compaction，那是框架专属
ctx.EndInvocation()   // ← 让 ctx.Ended() 为 true，跳过 run() 和 after 回调
return event, nil
```

## 三、LlmAgent：组合 base agent + 委托给`Flow`

> more read  ->. [Flow](/blog/adk-flow)

`llmagent.New`（`agent/llmagent/llmagent.go:39-137`）是最重要的一个构造器。它的核心手法是**组合**：

```go
// agent/llmagent/llmagent.go:102-115（精简）
baseAgent, err := agent.New(agent.Config{
    Name: cfg.Name, Description: cfg.Description, SubAgents: cfg.SubAgents,
    BeforeAgentCallbacks: cfg.BeforeAgentCallbacks,
    Run:                  a.run,          // ← 把 llmAgent.run 作为 base agent 的 Run
    AfterAgentCallbacks:  cfg.AfterAgentCallbacks,
})
a.Agent = baseAgent   // ← 一个 llmAgent「就是」一个 base agent
```

也就是说：**LlmAgent 本身没有重新实现 `Run` 骨架**，它复用了上面那套 before/run/after 循环，只是把 `run` 字段替换成自己的模型驱动逻辑 `llmAgent.run`。构造末尾还会 reveal 内部状态把 `AgentType` 标成 `TypeLLMAgent`（`llmagent.go:124`），并 `installTaskTools`（`llmagent.go:132`）——在 task 模式下注入 `finish_task` 工具、给每个子 Agent 装上 `single_turn` 或 `task` 的 agent-tool。

`llmAgent.run`（`llmagent.go:450-474`）构造一个 `llminternal.Flow`，接上默认的请求/响应处理器和全部模型/工具回调，然后 range `f.Run(ctx)`，对每个事件调 `maybeSaveOutputToState` 后 yield：

```go
// agent/llmagent/llmagent.go:450-467（精简）
func (a *llmAgent) run(ctx agent.InvocationContext) iter.Seq2[*session.Event, error] {
    f := &llminternal.Flow{
        Model:                a.model,
        RequestProcessors:    llminternal.DefaultRequestProcessors,
        ResponseProcessors:   llminternal.DefaultResponseProcessors,
        BeforeModelCallbacks: a.beforeModelCallbacks,
        // ...tool callbacks...
    }
    return func(yield func(*session.Event, error) bool) {
        for ev, err := range f.Run(ctx) {
            a.maybeSaveOutputToState(ev)          // 把最终文本写入 OutputKey 状态
            if !yield(ev, err) { return }
        }
    }
}
```

## 四、模型/工具回合循环（`internal/llminternal`）

真正的「思考—调用工具—再思考」发生在 `internal/llminternal/base_flow.go`。

`Flow` 结构体在 `base_flow.go:66-78`。它有两条处理器流水线（`base_flow.go:80-106`）：`DefaultRequestProcessors` 包含 basic、tool、auth、confirmation、**instructions**、identity、**compaction**、contents、**nl-planning**、**code-execution**、output-schema、agent-transfer 等一长串；响应处理器则是 NL-planning 与 code-execution 的后处理。**instruction、planner、code executor 都是请求处理器，而不是循环里的硬编码逻辑**——这点很重要。

外层回合循环 `Flow.Run`（`base_flow.go:122-170`）：反复调 `runOneStep`，直到最后一个事件 `IsFinalResponse()`（`base_flow.go:141`）为止；并有一个防呆——避免模型只吐「思考」事件而无限空转（`maxConsecutiveThoughtOnlyTurns = 10`，`base_flow.go:120`）。

单个回合 `Flow.runOneStep`（`base_flow.go:612-747`）是整篇的心脏：

```
runOneStep(ctx, req):
  1. preprocess: 跑请求处理器 + tool/toolset 预处理     base_flow.go:624
  2. 若处理器结束了 invocation → 短路                   base_flow.go:635
  3. callLLM:                                          base_flow.go:642 / 815
       ├─ 跑 Plugin + 用户 BeforeModelCallbacks
       │    任一返回响应则跳过真实模型调用             base_flow.go:827
       ├─ generateContent（按 RunConfig 决定是否流式）  base_flow.go:845
       ├─ 出错 → OnModelErrorCallbacks                  base_flow.go:852
       └─ 每个响应 → AfterModelCallbacks                base_flow.go:871
  4. postprocess: 跑响应处理器                          base_flow.go:647
  5. finalizeModelResponseEvent: 构造并 yield 模型事件   base_flow.go:672
  6. handleFunctionCalls: 执行工具调用                  base_flow.go:683
  7. 若响应设了 TransferToAgent：找到目标 Agent，
     就地运行并把它的整条事件流转发出来               base_flow.go:723
```

第 7 步解释了一个常见疑惑：为什么一次 `runner.Run` 会同时流出「transfer 事件」和「被转交 Agent 的响应」——因为转交是在同一个进程内 range 目标 Agent 的 `Run` 再 re-yield。

**工具执行** `Flow.handleFunctionCalls`（`base_flow.go:1160-1361`）：收集所有 `FunctionCalls`，每个 call 建一个 task，用 `platform.RunTasks` **默认并发**执行（`base_flow.go:1355`），再把并行响应合并（`base_flow.go:1468`）。每个工具的回调链在 `callTool`（`base_flow.go:1374-1419`）：

```go
// internal/llminternal/base_flow.go:1382-1387（精简）
if response == nil && err == nil {
    response, err = f.invokeBeforeToolCallbacks(toolCtx, tool, fArgs)
}
if response == nil && err == nil {
    response, err = tool.Run(toolCtx, fArgs)   // 若 before 回调已给出结果，此处被跳过
}
```

这里再次看到「callbacks over subclassing」的统一模式：before 回调可短路真实调用，after 回调总会跑。

> LlmAgent 还有第三种运行形态：作为 workflow 节点被驱动（`RunLLMAgentAsNode`，`agent/llmagent/llm_agent_wrapper.go:76`），按 `Mode`（chat / single_turn / task）分派。这与 task 委派、HITL 相关，留到《6 Workflow》再展开。

## 五、四种工作流 Agent -> workflowagents

这几个 Agent 都遵循同一个构造模式：**拒绝用户自定义 `Run`（工作流自己拥有循环）→ 把 `cfg.Run` 设成自己的方法 → 调 `agent.New` → reveal 内部状态标 `AgentType`**。

**SequentialAgent**（`agent/workflowagents/sequentialagent/agent.go`）
`New` 在 `48-70`，`Run` 在 `84-95`：按列表顺序把每个子 Agent 跑一遍，转发全部事件。还有 live 模式（`RunLive`，`131-220`）会给子 LLM Agent 注入 `task_completed` 工具，让每个知道该交棒了。

**LoopAgent**（`agent/workflowagents/loopagent/agent.go`）
`New` 在 `45-69`（配置里带 `MaxIterations`）。`Run` 在 `75-105`：无限 `for` 循环顺序跑子 Agent；**退出条件**是某个子 Agent 事件设了 `Actions.Escalate`（`loopagent/agent.go:88`）或达到 `MaxIterations`（`0` 表示一直跑到 escalate）：

```go
// agent/workflowagents/loopagent/agent.go:81-102（精简）
for _, subAgent := range ctx.Agent().SubAgents() {
    for event, err := range subAgent.Run(ctx) {
        if !yield(event, err) { return }
        if event != nil && event.Actions.Escalate { shouldExit = true }
    }
    if shouldExit { return }
}
if count > 0 { count--; if count == 0 { return } }
```

**ParallelAgent**（`agent/workflowagents/parallelagent/agent.go`）
`New` 在 `45-66`，`run` 在 `68-143`：用 `errgroup` 为每个子 Agent 起一个 goroutine，每个都拿到**自己的分支上下文**（`branch = parent.child`，`parallelagent/agent.go:83`）以隔离历史。结果通过 channel 汇聚，并带一个 ack 握手——让 runner 先把事件落库，生产者才继续（`runSubAgent`，`145-173`）。

**RemoteAgent（A2A v2）**（`agent/remoteagent/v2/a2a_agent.go`）
`NewA2A` 在 `325-362`，`run` 在 `368-496`：解析 agent card、建 A2A 客户端、把会话事件拼成消息，跑 `BeforeA2ARequestCallbacks`，然后按流式与否选 `SendMessage` / `SendStreamingMessage`，把每个 `a2a.Event` 转成 `session.Event`。安全上有两处硬化：`validateCardInterfaceOrigins`（`135-159`）把 card 声明的接口锁定在配置的源 origin；`AllowTransferToAgent`（`285-299`）默认 false，防止远程对端劫持本地控制流。

## 六、RunConfig

`agent/run_config.go` 刻意做得很小（`run_config.go:29-35`）：

```go
type RunConfig struct {
    StreamingMode             StreamingMode  // "none" | "sse"
    SaveInputBlobsAsArtifacts bool
}
```

- `StreamingMode`（`run_config.go:31`）：`callLLM` 据此决定是否流式生成（`base_flow.go:845`），远程 Agent 据此选 `SendMessage` vs `SendStreamingMessage`。
- `SaveInputBlobsAsArtifacts`（`run_config.go:34`）：为真时，runner 会把用户输入里的 blob（图片/文件）落成 artifact。

通过 `ctx.RunConfig()`（`agent.go:448`）访问；更完整的 live 运行配置另在 `internal/agent/runconfig`。

## 七、本篇要点

- **一个接口，多种实现**：Runner 和 Workflow 引擎只认那个六方法的 `agent.Agent`。Sequential / Loop / Parallel / Remote / Llm 全都是「换了 `run` 函数的 base agent」，因此可以任意嵌套。
- **构造走 New，而非实现接口**：未导出的 `internal()` 方法（`agent.go:52`）是闸门，`agent.New` 是唯一入口，各专用构造器内部都调它再打 `AgentType`。
- **回调而非继承**：agent 级、model 级、tool 级回调按序执行，第一个返回非 nil 内容/响应者短路其余；`BeforeAgentCallback` 的错误处理是个例外（见《5 Plugin》）。
- **迭代器即通用流**：组合就是 range 子 Agent 的 `Run` 再 re-yield，进程内 transfer 也是这么转发的。
- **状态不放 Agent 上**：工作流 Agent 把每轮状态放进 `session.State`，因此单个 Agent 实例可跨会话并发复用；ParallelAgent 则给每个子 Agent 分支上下文做隔离。
